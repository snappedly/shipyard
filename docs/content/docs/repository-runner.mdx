---
title: Repository runner
description: Wake a foreground Shipyard controller from labelled GitHub Issues.
---

The repository runner keeps one initialized GitHub.com repository ready for
work on an Apple Silicon Mac. It uses GitHub's official self-hosted Actions
runner only to deliver wake-up triggers. The foreground controller invokes the
repository's existing `npx shipyard run`; the Actions job does not own or report
the agent outcome.

## Install

You need Apple Silicon macOS, Docker Desktop, an initialized Shipyard
repository, `gh` authenticated with repository-administration access, and agent
credentials in `.shipyard/.env`.

The `GH_TOKEN` in `.shipyard/.env` is the issue-agent credential. Bundled issue
workflows need Contents, Issues, and Pull requests read/write permission plus
Metadata read permission to push a branch and publish a PR. Runner startup uses the host `gh` login for
administrative checks, including reading the published wake workflow. When
Shipyard runs in Docker, the runtime token is passed into that sandbox for
its GitHub issue operations; it is not the runner's administrative login.
Set `GH_TOKEN` to a nonempty value in `.shipyard/.env` before `runner start`;
startup stops immediately if the entry is missing or blank.

`npx shipyard init` automatically installs the repository runner after
scaffolding on supported Apple Silicon macOS hosts. Runner installation is
required for init to complete. Init stops with an error if the host is
unsupported or installation fails, and does not report completion. It keeps the
generated configuration and image; fix the reported issue, then run
`npx shipyard runner install` to retry against that setup.

After the runner installs, interactive init offers to commit and push
`.shipyard/` and the wake workflow to the current branch. It defaults to Yes
and leaves `.shipyard/.env` untracked. Non-interactive init skips this unless
you pass `--commit-setup true`. Runner start requires the wake workflow on the
default branch, so merge it there if init pushed another branch.

```sh
npx shipyard runner install
git add .shipyard .github/workflows/shipyard-wake.yml
git commit -m "Add Shipyard wake workflow"
git push
npx shipyard runner start
```

Terminal installs show a progress bar for validation, download, registration,
and workflow setup. Non-interactive output records the same stages as log
entries.

`--registration-token` can supply the one-time registration credential. It
does not replace administrative `gh` access, which is required to verify that
the repository has no conflicting `shipyard` runner.

The standalone `shipyard runner install` command never commits or pushes.
`shipyard runner start` requires the exact generated workflow on the default
branch. It validates the platform, repository,
installation, local Shipyard package, Docker, GitHub access, activation label,
credentials, and published workflow.

If an interactive install finds one or more existing repository runners with
the `shipyard` label, Shipyard shows their names and status and asks whether to
remove those GitHub registrations. Confirming removes the listed registrations
and retries installation; declining leaves them in place. Removal unregisters
the runners from GitHub but does not delete files on another machine. A
non-interactive install stops with the conflict details and never removes a
registration automatically.

## Wake and drain behavior

Only the exact lowercase GitHub issue label `shipyard` is eligible. Adding it
or manually dispatching **Shipyard wake-up** signals the controller. A
differently cased label, issue edit, or comment does not wake it.

The bundled issue templates install Snappedly skills and repository
dependencies inside their Docker sandbox. Shipyard runs `/triage` when it takes
an activated ticket, then rereads the issue. Triage checks the integration
branch, so a retry does not mistake work on its task branch for a completed
request. Only an open ticket carrying both
`shipyard` and `ready-for-agent`, with no conflicting triage state, can reach
implementation. Any other triage outcome follows the normal blocked flow:
`shipyard:blocked` is added, `shipyard` is removed, and the reason is commented
on the ticket. Standalone ready issues use `/implement`.
An activated planning spec or linked executable child becomes one
`/implement-spec` scope containing the parent, linked children labelled
`shipyard`, and their dependencies. Unlabelled children remain outside the work
scope. The selected template keeps its sequential or parallel planning,
implementation, and review stages. Parallel templates run ready child tickets
through scoped `/implement` workers, resolve cherry-pick conflicts during
integration, and merge each dependency wave into one spec branch. The complete
scope gets one open, non-draft PR per spec. Later selected tickets update the
same PR. The workflow never merges into the target branch or closes issues.
An open verified spec PR's `Source issues:` line can also link a newly labelled
ticket to that spec when no other parent link exists. Conflicting links block
the selected ticket for correction.
Selected tickets get `shipyard:pending` and lose `shipyard` when work starts.
Successful handoff replaces `shipyard:pending` with `shipyard:complete`.
It also removes `ready-for-human` from each completed issue.
The parent spec and existing PR show
`shipyard:blocked` if an unfinished child is blocked, `shipyard:outstanding-tasks`
if other children remain, or `shipyard:complete` when all linked tickets are
complete. Spec labels only report child state; they do not gate ticket selection.
The non-draft PR is ready for human review;
the issues remain open until the target repository's closure policy closes them. A
failed attempted scope gets an issue comment describing the failure. Shipyard
marks its selected issues `shipyard:blocked` and removes `ready-for-human`,
`shipyard:pending`, and `shipyard`, so they do not retry automatically. The
parent spec and existing PR reflect the block; failed work does not create a new
PR. Resolve the problem, remove `shipyard:blocked` from the ticket, and add
`shipyard` to retry; the spec label is recalculated.
Missing or conflicting relationships and invalid selected children receive
`shipyard:blocked` with an issue comment explaining the failure. If GitHub cannot confirm PR
readiness, Shipyard leaves activation in place so the next invocation can
reconcile the PR.
If a failure comment cannot be written, Shipyard retains a local pending report
under Git metadata. A fresh `shipyard` activation on an unblocked ticket
supersedes that report. Spec and PR status label errors are logged without
stopping ticket work; a later activation recalculates their labels.

Start always preflights the current backlog, recovering labels added while the
Mac was off. If work exists, it invokes exactly `npx shipyard run`. After a
successful invocation, an empty eligible issue set returns to idle, a changed
nonempty set starts another finite invocation, and an unchanged set records no
progress and returns to idle. A new label event, manual dispatch, or restart
retries no-progress work. Concurrent wake-ups are coalesced.

The workflow's result reports wake delivery only. Inspect the foreground
terminal, `npx shipyard runner status`, repository state, and
`.shipyard/runner/.shipyard-last-failure.json` for the Shipyard outcome. A
nonzero Shipyard exit or failed prerequisite records an actionable error and
takes the controller offline.

## Lifecycle

The controller runs only while its `runner start` terminal remains open. It
does not start at login. Ctrl-C, closing the terminal, and `runner stop` use the
bounded shutdown path and cancel active work while preserving Shipyard logs and
worktrees. `runner stop` can be run from another terminal: it signals the live
PID recorded by the repository even when the stored process identity is stale.

```sh
npx shipyard runner status
npx shipyard runner stop
npx shipyard runner remove
npx shipyard runner purge
```

Normal removal unregisters GitHub and deletes protected runner files, while
preserving Shipyard configuration, workflow, activation label, issues, logs,
and worktrees. If unregistration fails, local state is preserved. Use
`runner remove --force` only when necessary, then remove the named orphaned
registration in GitHub.

To remove the full Shipyard setup, including the package dependency and
repository configuration, run:

```sh
npx shipyard uninstall
```

Uninstall unregisters the repository runner, removes the entire `.shipyard/`
directory (including `.env` and runtime data), removes the generated wake
workflow when it still matches Shipyard's version, and removes
`@snappedly-tools/shipyard` with the repository's detected package manager. It
leaves GitHub issues and labels unchanged. Commit and push the workflow deletion
to disable it on GitHub. If the workflow was customized, uninstall preserves it
for manual review. In a non-interactive shell, pass `--yes`; if GitHub
unregistration fails, local runner files stay in place unless `--force` is
passed.

`runner purge` removes all dated default run-log folders and regular root-level
`.log` files regardless of age. Root-level `.log` files in `.shipyard/logs/`
are managed by this retention policy, including explicit logging paths. The
foreground controller separately removes dated folders older than eight
calendar days and root-level `.log` files last modified before the same cutoff.
It runs this maintenance at startup and once per day; a purge failure is
reported and does not stop the runner.

There is no Mac sleep detector. After a sleep beyond GitHub's 24-hour queue
lifetime, manually dispatch the workflow or restart the controller. GitHub can
remove registrations after 14 days offline; start re-registers a missing runner
using the current administrative `gh` login. A Mac rename requires explicit
remove and reinstall.

## Cost and trust

GitHub does not charge Actions minutes for the self-hosted wake job. The brief
exact-case gate runs on `ubuntu-latest` and may consume hosted Actions minutes
for private repositories. Model cost is incurred only when eligible work starts
Shipyard; the host owner still supplies the Mac, Docker, network, storage,
electricity, and model access.

Self-hosted runners on public repositories can expose the host to untrusted
repository activity. Use least-privilege credentials and tightly control label,
workflow, and collaborator authority. Runner binaries and credentials are
gitignored and protected under `.shipyard/runner/`, and isolated sandboxes
cannot mount or copy them. No-sandbox mode remains host-trusted by definition.
